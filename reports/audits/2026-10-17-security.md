### Low

#### L1. Background-job failures log full SQL bind parameters (amounts, descriptions, ids)

- **Where.**
  - `apps/api/src/recurring/recurring.service.ts:135-137` (`recurring_rule_failed ... ${error.message}`)
  - `apps/api/src/ledger/fx/fx.service.ts:262` (`fx_refresh_failed`)
  - `apps/api/src/sync/sync.service.ts:601` (`sync_prune_failed`)
- **Evidence.**
  - Drizzle's `DrizzleQueryError.message` is `Failed query: <sql>\nparams: <params>`
    (`node_modules/drizzle-orm/errors.js:12`).
  - The recurring insert binds these for every occurrence. They are `amount_minor`, `currency`,
    `description`, `account_id`, `category_id`, `workspace_id` and `created_by`
    (`recurring.service.ts:169-193`).
  - The FX backfill binds transaction ids and EUR amounts (`fx.service.ts` around line 212).
  - `ErrorFilter` already avoids this with `describeUnexpected` (`common/error.filter.ts:92-98`).
    These three call sites bypass it.
- **Scenario.**
  1. During a busy write period (an import, a family deletion, a burst of pushes),
     `lock_timeout` 10 s fires inside `RecurringService.catchUp`.
  2. The job logs up to 1000 rows of another user's amounts and descriptions to the Coolify
     logs.
  3. That breaks the documented invariant "Logs ... Never bodies, amounts, notes or tokens"
     (`docs/architecture.md`, Security).
- **Fix.** In all three places, log `describeUnexpected(error)` instead of `error.message`.

#### L2. The deploy script falls back to printing raw Coolify logs, hidden entries included, to public Actions logs

- **Where.** `scripts/coolify-deploy.sh:50-51`.
- **Evidence.**
  - The line is `jq ... 'map(select(.hidden != true) | .output)' ... || printf '%s\n' "$logs" >&2`.
  - When the second `jq` fails, the whole unfiltered log is printed. It fails when `logs` is not
    a JSON array, when it is truncated, or when Coolify changes the format.
  - The comment two lines above says hidden entries "can carry secrets and must never reach the
    public Actions log".
  - The repository is public, so Actions logs are public.
- **Mitigation already in place.** The token must not hold `read:sensitive`
  (`docs/operations.md` step 7). Coolify should then redact on its side. This finding is about
  the script failing open if that setting is ever wrong.
- **Fix.** Fail closed. Replace the fallback with
  `|| echo "Build log unreadable; see the Coolify UI." >&2`.

#### L3. A pending invitation token is stored in plaintext in `login_attempts.return_to` and can reach backups

- **Where.**
  - `apps/api/src/auth/auth.service.ts:48` stores `sanitizeReturnTo(returnTo)`.
  - `apps/web/src/features/family/invite-flow.tsx:114` sends
    `returnTo=/invite/<raw token>`.
- **Evidence.**
  - BR-8 says "Only the token's SHA-256 is stored".
  - A signed-out invitee who clicks "Join" creates a `login_attempts` row holding the raw token.
  - The row is deleted on callback. If the login is abandoned, it stays until the next
    `startLogin` after its 10-minute expiry.
  - A `pg_dump` taken in that window keeps it. Daily dumps are kept 14 days, plus weekly dumps
    and the off-host copy.
  - The invitation itself stays valid for up to 30 days.
- **Scenario.** Someone with read access to a dump or the off-host bucket accepts a still-pending
  invitation, joins the family and reads all family data. This needs backup access and an
  abandoned login, hence Low.
- **Fix (smallest).** Keep the token out of `returnTo`. Stash it in `sessionStorage` before the
  login redirect and return to a fixed `/invite`, which reads and clears it. The alternative is to
  strip `/invite/<token>` paths in `sanitizeReturnTo`.

#### L4. One user can saturate the single ledger write lock within their rate limit

- **Where.**
  - `apps/api/src/common/rate-limit.ts:31` (the `sync` limit, 120 pushes per minute)
  - `apps/api/src/sync/mutations.ts:15` (`PUSH_MAX = 200`)
  - `apps/api/src/sync/sync.service.ts:115-138` (one `ledgerTransaction` per mutation)
- **Evidence.**
  - The allowance is 120 × 200 = 24,000 mutations per minute per user.
  - The database audit measured a serialized ceiling of about 160 mutations/s, roughly 9,600 per
    minute. More clients add latency, not throughput.
  - Each waiting mutation holds one of the 10 pool connections.
- **Scenario.**
  1. One approved account replays fresh mutation ids in a loop across several concurrent
     requests.
  2. Every user's writes queue behind it.
  3. Many writes fail with `503 UNAVAILABLE` after `lock_timeout` 10 s.
  4. Reads slow down while they wait for pool connections.
- **Why Low.** Users must be approved by the owner at the provider.
- **Fix.** Budget mutations rather than requests. For example, add a second throttler keyed on
  the actor with `limit = 1200` per minute, charged by `mutations.length`. A simpler option is to
  lower the `sync` limit to 20 per minute, which still covers the 60 s heartbeat plus bursts.

### Hardening suggestions (not vulnerabilities today)

- **H1. The API trusts `X-Forwarded-For` from any private address and sits on the shared
  `coolify` network.**
  - Where. `bootstrap.ts:22` (`trust proxy 'loopback, linklocal, uniquelocal'`) and
    `nginx.conf:58-64`.
  - Any other container on that network can call `spending-api:3000` directly with a forged
    XFF. That evades the per-IP `auth` and `sensitive` budgets.
  - The `spending-api` alias could also collide with a service of the same name in another
    stack. Then nginx would proxy session cookies to it, which is the same reason the docs ban
    the `postgres` alias.
  - Fix. Set `trust proxy` to the web container's stack subnet only, or keep `api` on the stack
    network and give only the Postgres path the predefined network if Coolify allows it. Add
    `cap_drop: [NET_RAW]` (see H4) so co-tenants cannot ARP-spoof the plaintext
    nginx→api and api→Postgres hops.
- **H2. The XLSX reader bounds each part, not the total.**
  - Where. `apps/web/src/features/imports/xlsx.ts:9,56,74,85`.
  - Up to five parts of 64 MiB each are inflated and handed whole to `DOMParser`.
    `ROWS_MAX` is checked only after the full parse (`statement.ts:122`).
  - Only the user's own tab is affected (a self-DoS from a crafted file), because files never
    leave the device.
  - Fix. Cap the total inflated bytes (for example 32 MiB across parts), and stop once the
    sheet XML has more than `ROWS_MAX` `<row>` elements.
  - The PDF path is fine. It has a 10 MiB and 100-page limit and no WASM, and the worker runs
    under `script-src 'self'`. The DER walk rejects BER and truncation. Deep nesting throws
    `RangeError`, which `parseStatement` catches as `UNREADABLE`.
- **H3. Dependency.** `pnpm audit --prod` reports one moderate issue, js-yaml 5.0.0 to 5.4.0
  (GHSA-r3ph-w7gj-g6xm), via `@nestjs/swagger`. It is unreachable, because the API never parses
  YAML and the OpenAPI document is written only by a script. Fix. Add a pnpm `overrides` entry
  `js-yaml: ">=5.4.1"` or bump `@nestjs/swagger`. The other dependencies:
  - Runtime dependencies use caret ranges but install from a frozen lockfile in CI and Docker.
  - `pdfjs-dist` is pinned exactly.
  - Actions are pinned by SHA.
  - `allowBuilds` restricts install scripts.
- **H4. Docker hardening.** Missing from `docker-compose.yml` services:
  - `security_opt: [no-new-privileges:true]`
  - `cap_drop: [ALL]` (nginx on 8080 and node need no capabilities)
  - `read_only: true` with `tmpfs: /tmp` for `web` and `spending-api`
  - memory limits

  Base images are pinned by tag (`node:24.21.0-slim`, `nginx:1.30.5-alpine`,
  `postgres:18.6-alpine`) rather than by digest. All containers already run as non-root.

- **H5. Database role.** `spending_app` owns the database and runs both migrations and the app,
  so a SQL-level compromise could run DDL or `DROP`. Give migrations their own owner role, and
  grant the app only DML.
- **H6. `.dockerignore`.** The `.env` and `.env.*` entries (lines 10-11) match only at the
  context root, so `apps/api/.env` enters the build stage. It does not reach the final images,
  because only `dist`, `drizzle`, `node_modules` and `package.json` are copied. Use `**/.env` and
  `**/.env.*` to keep local secrets out of build layers too.
- **H7. Accepted risks, recorded for completeness.** Neither is reported as a finding.
  - The nginx error log keeps invitation tokens and callback `code`/`state`
    (`docs/operations.md`, Monitoring).
  - The offline local copy stays on the device after a `401` until the same user signs in or
    signs out (BR-34). On a shared device, the next person to open the app offline sees it.

## Areas checked and found sound

**Authentication and sessions**

- **Cookies.** `__Host-` prefix, HttpOnly, Secure, SameSite=Lax, Path=/. Production refuses
  `COOKIE_SECURE=false`.
- **Session token.** 32 random bytes; only the SHA-256 is stored.
- **Lifetimes.** Absolute 30 days, idle 14 days. Rotation every 24 h with a 60 s grace window
  for the old token; a superseded token never clears the new cookie.
- **Grant re-check.** Every 5 min; a conditional UPDATE lets one concurrent request claim it, and
  `invalid_grant` destroys the session.
- **Refresh and ID tokens.** Stored with AES-256-GCM.
- **Logout.** POST with CSRF; deletes the session row, revokes the refresh token and builds the
  RP-initiated logout URL.
- **Login fixation.** A login creates a new session and destroys the previous one.
- **OIDC.**
  - `state` (single-use, consumed before the exchange), nonce, and PKCE S256 are all checked.
  - Issuer, audience, expiry and RS256 signature are verified (`enableNonRepudiationChecks`).
  - The redirect URI is fixed and derived from `APP_ORIGIN`.
  - The login attempt is bound to the browser by a `__Host-` cookie (login CSRF), with a 10 min
    TTL.
  - Plain-http issuers are allowed only with `NODE_ENV=test`, and `NODE_ENV` defaults to
    production.
- **Redirect validation.** `sanitizeReturnTo` and `safeReturnTo` reject `//`, `/\`, control
  characters and paths that collapse to `//` after dot-segment normalization. The post-login
  target comes from the server-side attempt row, not the callback.
- **CSRF.** Every unsafe method needs the synchronizer token, compared in constant time, plus an
  exact `Origin`, or `Sec-Fetch-Site: same-origin` when `Origin` is absent. The global guard
  covers public routes too, and no public route accepts POST. CORS is off.

**Authorization (BR-1, BR-2, BR-3, BR-4, BR-7 to BR-12, BR-18a)**

- **The actor.** It comes only from the session cookie. No route takes a user id for itself.
  `@Public` is limited to login, callback, health and the invitation preview.
- **Sync push** (`decideUpsert`, `decideDelete`):
  - Membership is checked for both the target and the existing workspace, and a workspace the
    actor does not belong to returns `NOT_FOUND`.
  - Only the author may move a row.
  - Pending-review rows are refused.
  - BR-3. Only the author may pick their personal account. A null sent by a viewer who cannot see
    the account keeps the author's account.
  - BR-4. Category workspace, kind and archived state are checked.
  - BR-37. Transfer peers are checked across all workspaces, so a cross-workspace link is
    impossible.
  - A `mutationId` reused by another user is refused.
  - Replays and conflict results are presented through `ledgerRows`, which filters by
    visibility.
- **Sync pull.** It is scoped to the actor's memberships. Accounts outside them read as null.
  Tombstones are scoped to the actor's workspaces and suppressed when the row is visible live.
  Conflicts are only the actor's own, on rows still visible.
- **Conflict resolve.** Only the actor's conflict, and it must be the same transaction. It
  re-runs the full upsert or delete checks against the current version.
- **Imports:**
  - Create. The account must be live and in the actor's personal workspace.
  - Review, confirm and learn. These are limited to the actor's own pending or imported rows in
    the personal workspace. The category must be in the target workspace and of the right kind.
  - Transfer counterparts. They must be in the personal workspace, of the opposite kind, on
    another account and used once (`transferLinks`). Nonexistent and foreign ids get the same
    `INVALID_TRANSFER`.
  - Undo. It is limited to the actor's batch, and only to version-1 rows still in the personal
    workspace.
- **Ledger REST.** Every account and category write calls `requireMember` on the row's
  workspace. The history `accountId` filter is limited to visible accounts. Pending rows appear
  only from the personal workspace.
- **Recurring rules.** Load is followed by `requireMember`. The template reuses `referenceError`.
  A PATCH cannot change `workspaceId`. A hidden account is kept on null.
- **Budgets and analytics.** Both are scoped to memberships; categories come from the actor's
  own rows only.
- **Family:**
  - Owner actions use `lockOwnedFamily`, so a non-owner gets `403` and anyone outside the family
    gets `404`.
  - Invitations use a 256-bit token stored as SHA-256, a single-use conditional update and the
    same `410` for every failure. The preview reveals names only while pending.
  - Leave and remove drop the member's conflicts.
  - Deletion moves each row to its author's personal workspace, nulls family account references
    and splits cross-author transfers.
- **Account deletion.** Needs the typed confirmation. Personal data and sessions are removed by
  cascade, and authored family rows keep `created_by = null`. An owner of a family with other
  members must transfer first.
- **Export (BR-31).** Every section filters on the actor's memberships. Account ids from another
  member's personal workspace are nulled for transactions and rules. Import batches are the
  actor's only. Conflicts are the actor's only.

**Input, SQL and errors**

- **Input validation.** Every body uses zod `strictObject`, plus `ParseUUIDPipe` on ids. Limits:
  - JSON body 3 MB; nginx `client_max_body_size` 3 MB
  - 5000 import rows, 200 mutations per push, 500 confirm items
  - description 200 characters, note 2000, mapping 4 KiB
  - BR-13 amount ceiling, date range 1970 to 2100, and a strict cursor schema that survives a
    Date round trip
- **SQL.** Every `sql\`\``template binds its values. The only`sql.raw` calls are the constant
CHECK definitions (`schema.ts:76-78`). `ILIKE`input is escaped. The bulk`VALUES`in`confirm` and the backfill is built from bound parameters with casts.
- **Errors.** A fixed `{ code, message }` envelope. Validation details carry the path and issue
  code, never values. Unknown errors become `INTERNAL`. Request logs carry route, status,
  duration and request id only.

**Browser, headers and service worker**

- **CSP and headers** (ADR-011):
  - `script-src 'self'`; no inline script (the theme script is a file); `object-src 'none'`;
    `base-uri 'none'`
  - `frame-ancestors 'none'` plus `X-Frame-Options: DENY`; `form-action` limited to self and the
    provider; `img-src` limited to self, data, blob and Google avatars
  - HSTS, nosniff, `Referrer-Policy`, `Permissions-Policy`, COOP
  - The headers are re-included in every location that sets its own `add_header`
  - Source maps are deleted from the image and `*.map` returns 404
  - Swagger UI is not served
- **XSS sinks.** None. There is no `dangerouslySetInnerHTML` or `innerHTML`. `href` and `src`
  take only `loginHref` and the avatar URL (http or https, and CSP-limited).
- **Service worker.** It precaches only static `js`, `css`, `html` and `woff2`. `/api/` is on the
  navigation denylist and has no runtime cache. The only runtime cache is for the hashed pdf.js
  assets. Private data lives in a per-user IndexedDB that is deleted on sign-out and before
  another user's store opens.
- **CSV export.** Formula-leading cells get a `'`.

**Secrets, CI and infrastructure**

- **Secrets.**
  - No real secret is in the tree or the git history; only dummy smoke and e2e values.
  - The statement fixtures are synthetic (generator scripts say so).
  - `backup.sh` keeps the password out of argv.
  - The deploy token goes to curl through a file.
- **CI.** Actions are pinned by SHA. Deploy runs only from a successful `push` CI run on `main`,
  through the `production` environment. No `pull_request_target`.
- **nginx client IP.** `CF-Connecting-IP` is believed only from Cloudflare ranges, and the API
  receives a single XFF value.

## Recommendations

### Immediate

- L1. Use `describeUnexpected` in the three background-job log lines.
- L2. Remove the raw-log fallback in `coolify-deploy.sh`.

### Short Term

- L3. Keep invitation tokens out of `returnTo` and `login_attempts`.
- L4. Budget sync by mutation count, or lower the `sync` limit.
- H3. Override js-yaml to `>=5.4.1`.
- H6. Use `**/.env` in `.dockerignore`.

### Long Term

- H1, H4, H5. Narrow `trust proxy`, add container hardening, use a separate migration role, and
  pin image digests.
- H2. Add a total inflated-size cap and an early row cap in the XLSX reader.

## Overall Assessment

The security design is solid and is implemented consistently.

- One access policy is called on every workspace-scoped path.
- A non-member always gets `NOT_FOUND`.
- The BR-3 account hiding is applied in every reader (sync, REST, export, recurring and review).
- The OIDC BFF does state, nonce, PKCE, signature checks, browser binding, rotation and grant
  re-checks correctly.
- CSRF is layered (token plus Origin), and the CSP is strict for scripts.

No IDOR, injection, XSS, open redirect or cross-member data leak was found.

The four confirmed issues are Low:

1. Bind parameters in background-job logs
2. A fail-open log fallback in a public CI script
3. A plaintext invitation token that can reach backups
4. A per-user write budget that exceeds the global lock's capacity

The rest is defence-in-depth hardening of the shared Docker network and of the containers.
