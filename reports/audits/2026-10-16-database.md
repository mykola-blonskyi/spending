# Audit Report

Date: 2026-10-16

Auditor: Claude Code (read-only investigation)

Audit Type: Database (PostgreSQL 18 schema, queries, locking, retention, backups)

---

## Scope

- Schema and migrations `0000` to `0008` in `apps/api/drizzle`, `apps/api/src/database/schema.ts`,
  the `ledger_stamp`, `transaction_version` and `sync_tombstone_stamp` triggers, and
  `ledgerTransaction` with advisory lock 7302001.
- Every query site in `apps/api/src`: sync push and pull, ledger and history, analytics, budgets,
  recurring, imports, FX, sessions and login, access policy, family operations, export and
  account deletion.
- Production settings and statistics, read only.

Out of scope: the `categories.name` change for default categories, which another change is
handling. It is mentioned only where it touches a finding here.

## How it was measured

- **Scratch database.** `spending_audit` on the local PostgreSQL 18.6 container, built by applying
  all nine migrations. It was dropped after the audit.
- **Seed.**
  - 20 users, 2 families (4 and 3 members), 22 workspaces, 440 categories, 88 accounts.
  - 200,000 transactions over five years: 85% EUR, 15% USD, GBP or PLN, 165 of them unconverted.
    About 3% are soft-deleted, 10% edited, 2% pending review, and a third imported with a dedupe
    hash. Family 1 holds 50,000 rows, family 2 holds 30,000, and each personal workspace 6,000.
  - 217,470 `fx_rates` rows: 30 currencies of weekdays since 1999, the size of the full ECB
    history.
  - 133,334 `sync_mutations`, 2,000 `sync_tombstones`, 315 `sync_conflicts`, 60 sessions.
- **Queries.** Each query was rewritten by hand from its Drizzle builder, with the same
  predicates, joins, ordering and limits, and run with `EXPLAIN (ANALYZE, BUFFERS)`. Drizzle emits
  these builders almost one to one. Bind parameters were inlined.
- **Throughput.** `pgbench` replayed one sync push mutation. That is the same 11 statements
  `SyncService.push` issues for a new row, inside one transaction.
- **Production.** `ssh blonskyi` and `psql` under `default_transaction_read_only=on`. Only catalog
  and statistics queries were run, plus row counts. No data rows were read. Production holds 2
  users and 0 transactions, so its index statistics show nothing about the workload. Only its
  settings are evidence.
- **Caveat.** Timings come from Docker on a laptop. Production shares one small VPS and
  `shared_buffers` of 128 MB with eight other databases. Read the numbers as ratios, not as
  production latency.

## Summary

At household scale the database is in good shape. Every query a user triggers ran under 60 ms
at 200,000 rows, and most ran under 1 ms. Money is integer minor units, dates are `date`, and
enums are real enums. Foreign keys that cascade are indexed. The isolation choices match the
sync design.

The findings that matter are not about speed. A backup restore silently breaks sync for every
device. The API has no timeouts at any layer, so one stuck writer can stall every request. The
rest are small cleanups and missing guard rails.

## Findings

Ranked by impact times confidence. Each finding has its evidence, the smallest change, and its
migration risk.

### High

#### 1. Restoring a backup rewinds the sync revision sequence, and devices then skip new writes

**Impact.** High, but only on the day of a restore. **Confidence.** High.

- `pg_dump` stores the sequence at dump time. Seen on the scratch database:
  `SELECT pg_catalog.setval('public.ledger_revision', 491180, true);`.
- After a restore, new writes take revisions from the dump-time value again.
- A device whose cursor is past that value asks for `revision > cursor`. It never receives those
  new rows, edits or deletes until the sequence passes its old cursor. Nothing tells it.
- The web client resets its cursor only when a new workspace appears
  (`apps/web/src/data/sync/pull.ts:108`).
- The same devices keep rows that the restore lost, and keep newer versions of rows the restore
  reverted. They are never told about either.
- The restore runbook in `docs/operations.md` ("Backups and restore") does not mention the
  sequence.

**Smallest change.** Add one step to the runbook, run on `spending_restore` before the swap.

```sql
SELECT setval('ledger_revision', (SELECT last_value FROM ledger_revision) + 1000000000);
```

That makes every later write visible to every device again. It does not remove the ghost rows
on devices. A complete fix needs devices to resync from cursor 0 after a restore. One way is an
"epoch" value that `/sync/pull` returns and that changes on restore. On a change, the client
resets its cursor to 0 and drops its local rows. That is a product decision, because local
unsent changes would need the same handling as BR-34. Until then, the runbook can ask users to
sign out and back in on each device. Under BR-34 a sign-out deletes the local store, so the next
sign-in pulls from cursor 0.

**Risk.** None for the runbook step. The sequence is `bigint`, so a gap of 10^9 costs nothing.

### Medium

#### 2. No timeouts at any layer, behind a 10-connection pool and one global write lock

**Impact.** Medium. **Confidence.** High for the configuration. The stall itself is inferred
from the code and was not reproduced.

- Production settings (read only): `statement_timeout = 0`, `lock_timeout = 0`,
  `idle_in_transaction_session_timeout = 0`.
- `apps/api/src/database/database.module.ts` creates `new Pool({ max: 10, idleTimeoutMillis })`
  with no `connectionTimeoutMillis`. In node-postgres that waits forever for a free connection.
- `ledgerTransaction` takes a pool connection first and then waits on
  `pg_advisory_xact_lock(7302001)`. Writers queue while each holds a connection.
- Once 10 writers wait, every other request waits too, including `SessionService.authenticate`,
  which runs on every API call. Nothing ever times out. The API stalls until the lock holder
  finishes. A holder that never finishes, from a future bug or a hung connection, stalls the
  API for good.
- Measured lock hold times on the seed:

  | Holder                                                | Time under the ledger lock |
  | ----------------------------------------------------- | -------------------------- |
  | Family deletion, move of 50,000 rows (`purge` update) | 1,444 ms                   |
  | Account deletion of a user with 6,000 rows            | 58 ms                      |
  | Import of 5,000 rows                                  | 132 ms                     |
  | FX backfill pass over 29,244 non-EUR rows             | 151 ms                     |
  | One sync mutation (11 statements)                     | about 6 ms                 |

- `pgbench` on one push mutation:

  | Clients | Explicit early lock (today)     | Without it (trigger still locks) |
  | ------- | ------------------------------- | -------------------------------- |
  | 1       | 160 to 172 per s, 5.8 to 6.2 ms | same                             |
  | 8       | 159 to 201 per s, 40 to 50 ms   | 355 to 387 per s, 21 to 23 ms    |

  More clients add latency, not throughput. That confirms ADR-006: writes are serialized. The
  ceiling of about 160 mutations per second is far above household need. It is listed here only
  because the queue holds pool connections while it waits.

**Smallest change.** Three options in the existing `Pool` constructor, versioned with the code
and applied to every connection:

```ts
new Pool({
  connectionString: config.databaseUrl,
  max: 10,
  idleTimeoutMillis: 30_000,
  connectionTimeoutMillis: 10_000,
  statement_timeout: 30_000,
  idle_in_transaction_session_timeout: 60_000,
});
```

`statement_timeout` also caps time spent waiting for the advisory lock. 30 s is 20 times the
longest measured holder. A timed-out push fails one mutation, and the client retries it
idempotently (BR-18). Optionally add `set local lock_timeout = '10s'` before the advisory lock
in `ledgerTransaction`. That makes a long queue fail fast instead of holding connections.

**Risk.** Low. The FX full-history store runs many statements of 1,000 rows each, and each
statement is far below 30 s. Check `/api/health/ready` and the backup container, which use
their own connections.

### Low

#### 3. The FX backfill rescans the whole non-EUR history under the global lock every 6 hours

**Impact.** Low today. It grows linearly with history. **Confidence.** High.

- `FxService.backfill` walks `transactions` by `id` and runs a lateral `fx_rates` lookup for
  every non-EUR row. It locks the matches `FOR UPDATE` while it holds the ledger lock.
- One batch visited 29,244 rows to find 160 candidates, in 151 ms.
- A row converted at its own day's rate (`fx_rate_date = occurred_on`) can never get a closer
  rate, because the lookup only considers dates up to `occurred_on`. So
  `fx_rate_date is null or fx_rate_date < occurred_on` is already implied by the existing
  predicate.

**Smallest change.** State that implied predicate in the query and add a partial index that
matches it:

```sql
CREATE INDEX transactions_fx_pending_idx ON transactions (id)
  WHERE currency <> 'EUR' AND deleted_at IS NULL
    AND (fx_rate_date IS NULL OR fx_rate_date < occurred_on);
```

Measured after shifting weekend rows to Friday's rate date, as in real data: 151 ms became
19 ms, with 8,360 rows visited instead of 29,244. The index is 280 kB at 200,000 rows. The
results are the same, because the predicate is already implied.

**Risk.** It is a plain `CREATE INDEX` inside the migration transaction. It is safe, because
the site is down while migrations run (see finding 9).

#### 4. Documented invariants with no CHECK constraint

**Impact.** Low. They are defence in depth behind validation that already exists.
**Confidence.** High.

| Rule                                             | Where it is enforced now | Missing constraint                                                                               |
| ------------------------------------------------ | ------------------------ | ------------------------------------------------------------------------------------------------ |
| BR-13: amount at most 10^12                      | zod only                 | `amount_minor <= 1000000000000` on `transactions`, `budgets`, `recurring_rules`                  |
| BR-20: a resolved conflict has a resolution      | service                  | `sync_conflicts`: `(status = 'resolved') = (resolution is not null and resolved_at is not null)` |
| A rule ends after it starts                      | service                  | `recurring_rules`: `ends_on is null or ends_on >= starts_on`                                     |
| An invitation is accepted or revoked, never both | service                  | `invitations`: `accepted_at is null or revoked_at is null`                                       |

The BR-13 cap is what keeps analytics safe. `AnalyticsService.sums` turns a PostgreSQL
`numeric` sum into a JS number with `Number()`. Without the cap, a few thousand oversized rows
written by a bug or a direct SQL fix would lose precision without any error.

**Risk.** `ADD CONSTRAINT ... CHECK` scans the table under an exclusive lock. That takes
milliseconds at today's size, and the site is down during migrations anyway. Run a `SELECT` for
violating rows first.

#### 5. `categories.system_key` is not unique per workspace

**Impact.** Low. **Confidence.** Medium.

- `loadCatalog` builds `Map(systemKey -> category)`. If a key appears twice, the last row wins.
- Family deletion (`FamilyService.purge`) contains an explicit `exists (... system_key ...)`
  check to avoid creating a second row with the same key. That shows the invariant is real but
  only implied.

**Smallest change.**
`CREATE UNIQUE INDEX categories_system_key_uq ON categories (workspace_id, system_key) WHERE system_key IS NOT NULL;`.
Fold it into the pending `categories.name` work rather than a separate migration, because that
work changes how default categories are identified.

#### 6. One redundant index and one the cleanup query cannot use

**Impact.** Low. **Confidence.** High.

- `accounts_workspace_idx (workspace_id)` is a prefix of `accounts_name_uq (workspace_id, kind,
name)`. Every `workspace_id = ?` or `IN (...)` lookup can use the unique index. Drop it.
- `sessions_expires_idx` cannot serve `SessionService.deleteExpired`. Its predicate
  `expires_at < now() OR last_seen_at < now() - 14 days` needs both columns, and `last_seen_at`
  has no index. The plan is a sequential scan. Keep the index and leave the query as it is.
  Sessions are a few rows per user. This is noted only so nobody "fixes" it later by adding a
  `last_seen_at` index, which `touch()` would then have to maintain on every update.

**Risk.** `DROP INDEX` is instant.

#### 7. `sync_mutations` grows forever, and 0006 dropped the index a cleanup would need

**Impact.** Low. **Confidence.** High.

- Nothing deletes `sync_mutations` rows except account deletion. The seed's 133,334 rows take
  26 MB with indexes, about 200 bytes per mutation. A household making 20 edits a day adds
  about 1.5 MB a year.
- Migration 0006 dropped `sync_mutations_created_idx` as unused, so a time-based purge would scan
  the table.
- Resolved `sync_conflicts` rows also stay forever. They are tiny.

**Smallest change.** Nothing now. When the table passes about a million rows, delete rows older
than 90 days in the existing session cleanup path, which can run as a sequential scan.

**Tradeoff.** BR-18 dedupe only holds inside the retention window. A device that lost a push
response and then stayed offline longer than 90 days could re-apply that mutation once. The
retry would hit the version check (BR-19), so the worst outcome is a conflict, not a duplicate
row.

#### 8. Display text stored instead of a key: `workspaces.name = 'Personal'`

**Impact.** Low. **Confidence.** High.

- `UsersService.provision` stores the English word `'Personal'` as every personal workspace's
  name.
- The web never shows it. `accounts-page.tsx` uses `t('personal')`, keyed by `kind`.
- It does reach clients through `/sync/pull` workspaces and the JSON export, in English for
  every locale.

**Smallest change.** Store `''` for personal workspaces and have clients label them by `kind`,
as they already do. Update existing rows in the same migration.

Not repeated here: `FamilyService.purge` re-links categories by `name`. It belongs to the
pending `categories.name` change.

No other display-text columns were found. `fx_source` and `fx_rates.source` hold the key
`ecb`. Import rejections store reason codes. Authors are referenced by id, and names are joined
at read time.

#### 9. Migration runner facts the docs get slightly wrong

**Impact.** Low. **Confidence.** High. This was checked in
`drizzle-orm@0.45.4/pg-core/dialect.js`.

- `migrate()` applies all pending migrations in one transaction. The comment in
  `apps/api/src/database/migrate.ts` ("Each migration runs in a transaction") reads as one
  transaction per migration. All-or-nothing is the
  better behaviour. Fix the comment.
- `CREATE INDEX CONCURRENTLY` cannot run there. It is also not needed, because the deploy stops
  the API while `migrate` runs (`docs/operations.md`, Production topology). Locking DDL is safe
  as long as that stays true.
- `ALTER TYPE ... ADD VALUE` followed by any use of the new value in the same deploy fails with
  "unsafe use of new value". Ship the new enum value and its first use in separate deploys.
- A pending migration is applied only when its journal `when` is newer than the last applied
  one. A branch merged with an older timestamp is silently skipped. Regenerate the migration
  after rebasing.

**Smallest change.** Correct the comment and add these three lines to `apps/api/drizzle`'s
migration notes.

#### 10. No slow-query visibility

**Impact.** Low. **Confidence.** High.

- Production has `log_min_duration_statement = -1`, no `pg_stat_statements`, and
  `track_io_timing = off`. A query that turns slow as data grows would go unnoticed.
- The instance is shared with eight other databases. A server-wide change belongs to whoever
  runs that instance.

**Smallest change.** `ALTER DATABASE spending SET log_min_duration_statement = '500ms';`, run once
by the superuser. It affects only this database, and only for new connections.

## Not worth doing

| Idea                                                                                | Why not, with numbers                                                                                                                                                                                                                                                                                                      |
| ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Index `transactions (workspace_id, revision)`                                       | Helps a solo user pulling behind busy families (2.0 ms to 0.4 ms) and workspace cascades (16.5 ms to 0.8 ms). Replacing `transactions_revision_idx` with it would make a family user's first pull sort every matching row. Adding it means a tenth index to write on the hottest table. Revisit past about 5 million rows. |
| Full-key history index `(workspace_id, occurred_on desc, created_at desc, id desc)` | One workspace: 54 ms to 0.05 ms. Two workspaces (the default) still need a sort, 15 ms. Server-side history serves only export and API clients (ADR-006), because the web reads its local store. Revisit if an API client pages history heavily.                                                                           |
| Covering index for analytics                                                        | 44 ms for five years of two workspaces. Not a bottleneck.                                                                                                                                                                                                                                                                  |
| Removing the early advisory lock in `ledgerTransaction`                             | Would double the throughput ceiling (about 370 per s instead of 180 per s at 8 clients), but brings back the deadlock risk ADR-006 describes. The current ceiling is about 100 times household need.                                                                                                                       |
| Fewer round trips per push mutation                                                 | Memberships are read 2 to 3 times per mutation (11 statements, about 6 ms). A 200-mutation push takes about 1.2 s. Fine at the 120 pushes per minute rate limit.                                                                                                                                                           |
| Hard-deleting soft-deleted transactions                                             | Tombstones are rows with `deleted_at`. Sync needs them, and BR-30 keeps their dedupe keys. About 3% of rows.                                                                                                                                                                                                               |
| Pruning `fx_rates`                                                                  | The full ECB history is 217,000 rows, 16 MB. `max(date)` scans it in 20 ms every 6 hours.                                                                                                                                                                                                                                  |
| Composite FKs for "category in the same workspace" (BR-4)                           | Needs `ON DELETE SET NULL (category_id)` column lists. Categories are never hard-deleted except with their workspace, and the service already enforces BR-4.                                                                                                                                                               |
| Converting `color`, `icon`, `timezone` or `fx_source` to enums                      | They are keys, not display text. Enum changes cost a deploy each (finding 9).                                                                                                                                                                                                                                              |
| WAL archiving and point-in-time recovery                                            | The recovery point is up to 24 hours, from the daily dump. For a household app with offline clients that is an accepted, documented tradeoff. It is the first thing to revisit if more people use the app. The offsite copy sits on the same VPS (`docs/operations.md` says so).                                           |

## Recommendations

### Immediate

- Add the sequence bump to the restore runbook (finding 1).
- Add the pool and session timeouts (finding 2).

### Short Term

- One migration with the CHECK constraints (4), the FX partial index (3), dropping
  `accounts_workspace_idx` (6), and personal workspace names (8). Fold the `system_key` unique
  index (5) into the `categories.name` change.
- Fix the `migrate.ts` comment and add the migration notes (9).
- Turn on the slow-query log for the `spending` database (10).

### Long Term

- Decide whether devices should detect a restore (a sync epoch) and resync from 0 (finding 1).
- Purge old `sync_mutations` once the table is large (7).

---

## Overall Assessment

The schema follows its own rules closely. Integers for money, enums for closed sets, ids instead
of names, indexed cascades, and one revision sequence under one lock. At 200,000 transactions
nothing a user triggers is slow. The global write lock caps writes at about 160 mutations per
second, which is plenty. The real exposures are operational. A restore silently desynchronises
devices, and nothing bounds how long a request can wait.
